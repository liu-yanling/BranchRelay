## 六、数据、资产与状态

- 持久化：SQLite（`data/branchrelay.db`，加入 `.gitignore`）；表结构见 `app/models/`。
- 数据表：`users` / `tasks` / `events` / `notifications`（`report_drafts` 留到 2-2/2-3）。
- 状态机（本阶段用到）：`待办理` / `办理中` / `待复核` / `待补充` / `已完成`。
  - `start`：待办理→办理中（经办人）
  - `update_progress`：办理中/待补充→不变（经办人）
  - `submit_review`：办理中/待补充→待复核（经办人，必填交付说明，转给复核人）
  - `reject`：待复核→待补充（复核人，必填退回原因，转回经办人）
  - `approve`：待复核→已完成（复核人，记录完成时间，通知发起人+经办人去重）
- 版本号：任务每次操作 `version+1`，写入前校验当前处理人、状态、版本，拒绝越权与过期操作。

## 七、API / 工具设计

统一错误结构：`{"error": {"code": "...", "message": "..."}}`，HTTP 状态码 400/403/404/409。

| 接口 | 方法 | 请求体 | 响应 | 错误 |
| --- | --- | --- | --- | --- |
| `/api/bootstrap` | GET | — | 用户列表、演示时间 | 无 |
| `/api/reset` | POST | — | ok + 演示时间 | 无 |
| `/api/tasks?view=&role=` | GET | — | `{tasks:[...]}` | 未知身份/视图 |
| `/api/tasks/{id}?role=` | GET | — | 任务详情 + 事件时间线 | 404/403 |
| `/api/tasks` | POST | `TaskCreate` | 新任务 | 400 校验失败 |
| `/api/tasks/{id}/action` | POST | `TaskAction` | 更新后任务 | 400/403/409 |
| `/api/board?role=&filter=` | GET | — | 统计 + 任务列表 | 403 仅负责人 |
| `/api/notifications?role=` | GET | — | 通知列表 + 未读数 | 未知身份 |
| `/api/notifications/{id}/read` | POST | — | ok | — |

Pydantic 校验规则（`schemas/`）：
- `TaskCreate`：标题/说明/计划日/截止时间/经办人/复核人；标题、两岗位、计划日、截止必填；经办人≠复核人；截止不早于计划日。
- `TaskAction`：`action` 枚举、`note`（提交/退回必填）、`version` 整数。

## 十、测试要求

- 第一层 mock 测试（本阶段，全离线，不调模型）：
  1. `test_create_task`：合法创建、经办人=复核人被拒、截止早于计划日被拒、非综合岗创建被拒
  2. `test_submit_review`：办理中→待复核、必填交付说明、转给复核人、生成通知
  3. `test_reject`：待复核→待补充、必填原因、转回经办人、意见可见
  4. `test_approve`：待复核→已完成、无当前处理人、记录完成时间、通知去重
  5. `test_permission`：经办人复核被拒（403）、非处理人操作被拒
  6. `test_version_conflict`：同版本重复操作被拒（409）、只生成一条有效记录
  7. `test_error_shape`：错误响应统一为 `{"error":{"code","message"}}`
- 第二层真实冒烟：本阶段不涉及（2-2 引入）。
- 数据恢复：2-3 引入 `scripts/restart-check.sh`。
